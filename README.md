# Agentic RAG over six public energy documents

A retrieval-augmented question-answering system over public energy documents, with a retrieval and answer evaluation.
It answers questions **only from the documents** and says so when the documents do not contain the answer.

**Corpus (six public documents):** Equinor Annual Report 2025; four Havtil regulations in English (Framework, Management,
Activities, CO2 Safety, version 1.1.25); IRENA, *Renewable Power Generation Costs in 2024*. Not affiliated with Equinor,
Havtil or IRENA. The PDFs, chunks and indexes are not in this repository (see "Reproducing").

IRENA (2025), *Renewable power generation costs in 2024*, International Renewable Energy Agency, Abu Dhabi.

## Findings in brief

- **Hybrid retrieval ranks better than vector-only search in the easy tier.** On the first test run, hybrid (BM25 plus vectors)
  put the right passage higher than vector search (MRR and nDCG); it did not clearly find it more often.
- **A cross-encoder reranker showed no supported gain** over hybrid in any tier, at much higher latency.
- **Retrieval matters far more than the model's own knowledge.** Closed-book (no passages) answers are near zero except a small
  leakage effect in the easy tier; with retrieval, correctness is far higher in every tier (see the tables).
- **gpt-5-mini beats gpt-5-nano** in every tier (paired intervals exclude 0).
- **The tool-calling agent showed no supported gain over the fixed pipeline** (one hybrid search, then answer). It was run once,
  on the dev split only. It answered some near-miss unanswerable questions that the fixed pipeline refused and used about twice
  the tokens, so the fixed pipeline is the recommended default. An earlier query-rewriting variant also showed no gain.

> **Evaluation approach.** The 199 evaluation questions are synthetic: generated by language models (Gemini and Claude) from the
> cleaned source text, each with gold evidence (document, page, quote) that a script checks against the cited page, and split
> into dev and test. Answers are scored against reference answers by an LLM judge (Claude). This is a common low-cost way to
> evaluate a RAG system; its biases are listed under "Limitations and disclosures". Every number below is rendered from
> `results/results.json` by `eval/make_readme.py`; none is typed by hand.

## What is in it

1. **Parsing, cleaning and chunking** (`src/rag/parse.py`, `clean.py`, `chunk.py`): PDF to per-page markdown, page filtering,
   heading-aware chunks of at most 400 tokens that keep document, page and heading path; tables stay whole with their caption.
2. **Retrieval** (`src/rag/retrieve.py`): one entry point `search(query, mode, k)` with three modes: `vector` (bge-small embeddings
   in ChromaDB), `hybrid` (BM25 plus vectors, fused with our own reciprocal rank fusion) and `hybrid_rerank` (a MiniLM
   cross-encoder over the top 30). Table chunks are embedded with an LLM-written summary in front of them.
3. **Generation** (`src/rag/generation.py`): the model answers from numbered passages and replies in JSON with a status
   (`answered`, `not_in_context`, `ambiguous`) and the passage numbers it used.
4. **Agent** (`src/rag/agent.py`): a LangGraph graph where the model can call one tool, `search_documents`, up to three times.
   It is restricted to the documents by its prompt and by three guardrails (input length cap, refusal of off-topic requests
   without searching, and discarding any "answered" reply that had no passage behind it).
5. **LLM client** (`src/rag/llm.py`): LangChain model access, with a response cache by prompt hash, retries, a call log and a hard
   budget cap. Total spend on all experiments stayed under the cap of USD 1.00.
6. **Evaluation** (`eval/`): own implementations of hit@k, coverage@k, MRR@k and nDCG@k, bootstrap confidence intervals and paired
   bootstrap differences (`src/rag/metrics.py`, `stats.py`), with unit tests (`tests/`).

## How the questions were made

199 questions in three tiers, always reported separately and never blended:

| Tier | Written by | Character |
|---|---|---|
| Round 1 | Gemini | natural wording, mostly one page, easy |
| Round 2 | Gemini | hard, multi-page, wording deliberately swapped for synonyms (a paraphrase stress test, so the wording is unnatural) |
| Round 3 | a Claude subagent | natural wording, mostly multi-page |

Questions are split into a `dev` set (used to choose settings) and a `test` set. Gold labels are evidence (document, page, a
quote of at most 25 words), never chunk ids. Behaviours: answerable, unanswerable (not in the corpus), unanswerable-near (the
document is close but does not state it) and ambiguous.

## Results

### Retrieval, test split, second run (`retrieval_test_tablesum2`; answerable, non-holistic questions)

| Tier | n | Mode | hit@10 [95% CI] | MRR@10 [95% CI] |
|---|---|---|---|---|
| Round 1 (easy, natural) | 45 | vector | 0.91 [0.82, 0.98] | 0.66 [0.55, 0.77] |
| Round 1 (easy, natural) | 45 | hybrid | 0.93 [0.84, 1.00] | 0.79 [0.69, 0.89] |
| Round 1 (easy, natural) | 45 | hybrid_rerank | 0.93 [0.84, 1.00] | 0.76 [0.65, 0.86] |
| Round 2 (hard, synonym-swapped) | 41 | vector | 0.80 [0.68, 0.93] | 0.49 [0.36, 0.61] |
| Round 2 (hard, synonym-swapped) | 41 | hybrid | 0.90 [0.80, 0.98] | 0.54 [0.41, 0.66] |
| Round 2 (hard, synonym-swapped) | 41 | hybrid_rerank | 0.78 [0.66, 0.90] | 0.49 [0.36, 0.61] |
| Round 3 (multi-page, Claude-written) | 29 | vector | 0.86 [0.72, 0.97] | 0.77 [0.62, 0.91] |
| Round 3 (multi-page, Claude-written) | 29 | hybrid | 0.93 [0.83, 1.00] | 0.86 [0.74, 0.96] |
| Round 3 (multi-page, Claude-written) | 29 | hybrid_rerank | 0.93 [0.83, 1.00] | 0.81 [0.67, 0.93] |

Mean latency per query: vector 0.021 s, hybrid 0.023 s, hybrid_rerank 0.865 s.

Intervals overlap in most comparisons, so **no ranking of the three modes is claimed**. The one supported finding is on the
first test run (results key `retrieval_test_final`): hybrid ranks the right chunk higher than vector search in the easy tier
(MRR and nDCG), not that it finds it more often. The reranker showed no supported gain over hybrid in any tier and its latency is far higher (see
above), so hybrid is the default. Table questions are the weak spot (`breakdowns` in `results.json`).

| Round 3 (multi-page, Claude-written) | 29 | 0.00 [0.00, 0.00] | 0.03 [0.00, 0.10] |

Paired difference on the same questions (second minus first; an interval containing 0 means no difference is claimed):

- Round 1 (easy, natural): mini, no passages minus nano, no passages: +0.174 [+0.065, +0.283] (n = 46)
- Round 2 (hard, synonym-swapped): mini, no passages minus nano, no passages: +0.023 [+0.000, +0.068] (n = 44)

|---|---|---|---|

| Round 3 (multi-page, Claude-written) | 13 | 0.62 [0.38, 0.85] | 0.77 [0.54, 1.00] |

Paired difference on the same questions (second minus first; an interval containing 0 means no difference is claimed):

- Round 1 (easy, natural): tool-calling agent (mini) minus fixed pipeline (mini): +0.000 [+0.000, +0.000] (n = 21)
- Round 2 (hard, synonym-swapped): tool-calling agent (mini) minus fixed pipeline (mini): -0.095 [-0.286, +0.095] (n = 21)
- Round 3 (multi-page, Claude-written): tool-calling agent (mini) minus fixed pipeline (mini): +0.154 [+0.000, +0.385] (n = 13)

| Question kind | n | fixed pipeline (mini) (judged correct / status) | tool-calling agent (mini) (judged correct / status) |
|---|---|---|---|
| unanswerable_out | 1 | yes 1 / not_in_context 1 | yes 1 / not_in_context 1 |
| unanswerable_near | 5 | yes 5 / not_in_context 5 | no 2, partly 1, yes 2 / answered 4, not_in_context 1 |
| ambiguous | 1 | no 1 / answered 1 | no 1 / answered 1 |

The agent found the gold evidence for more questions, but no paired interval excludes 0 in any tier, so **no difference in
correctness is claimed**. On near-miss unanswerable questions it answered some that the fixed pipeline refused, including one
that confuses the buyer of a 40% interest with the buyer of the remaining 20%. It uses about twice the tokens. The fixed
pipeline (one hybrid search, then answer) is therefore the recommended default. A "faithful" figure for the agent is not
reported: faithfulness was not judged for that run. An earlier agent variant that rewrote queries and retried after a refusal was
also tried on dev (`rewrite.py`, keys `rewrite_dev_*` and `gated_dev_gate1`); it showed no supported gain and is kept as a
negative result.

## Limitations and disclosures

- **Synthetic question set, one non-expert reviewer.** Questions were generated by language models (Gemini for rounds 1 and 2,
  a Claude subagent for round 3, plus 30 rewrites by Claude), screened by an LLM pre-screen, and given gold evidence that a
  script checks is on the cited page (which proves only that the quote is on that page). The author read the Gemini questions
  and the 30 rewrites and raised no objections, but is not an energy domain expert and there was no second reviewer; a domain
  expert's review is still needed. Round 3 has no recorded human reading. The review log (`eval/review_log.jsonl`) records the
  accept, edit and reject decisions but no per-item reading, so its rejection count is not a measure of question quality.
  Generated questions also tend to reuse the source's vocabulary, and a generator can favour phrasing that similar models
  handle well; round 2 counters the first by swapping standard terms for synonyms.
- **LLM-as-judge.** Answers were scored against the reference answers by an LLM judge (Claude), mostly from truncated answer
  text. Claude also wrote round 3 and the rewrites, so it may favour them. Agreement with a human judge was not measured
  systematically (a few dev items were double-checked). Strict scoring counts only "yes"; lenient numbers are in `results.json`.
- **The test split was looked at several times.** Retrieval ran on test twice (`retrieval_test_final`, then
  `retrieval_test_tablesum2` after changes chosen on dev), so the second run is not a clean one-shot. About eight retrieval
  configurations were tried on the same dev questions, and many paired intervals were examined, so a single supported interval is
  weak evidence. Generation and closed-book runs on test used settings fixed on dev.
- **Small n.** Per-tier counts are in the tables; the unanswerable and ambiguous groups have only a handful of questions each.
- **Nondeterministic models.** gpt-5-nano and gpt-5-mini run with reasoning effort "minimal" and no temperature setting, so
  repeat runs can differ; the cache is what repeats a run exactly. Cost figures use OpenAI's published list prices (checked
  18 Nov 2026), so they estimate list-price spend, not an invoice.
- **Table summaries** were written by a model that resembles the question generators, which can flatter the table gain compared
  with real user phrasing.
- **Parsing losses.** Table rows are retrieved poorly, text inside figures is lost, heading levels are noisy, and numeric table
  rows are the main source of retrieval misses.
- **Closed-book leakage** is measured above, not eliminated: the Havtil regulations and IRENA reports are public and may be in
  the models' training data.
- **Not done:** a download script and fresh-clone test, a live demo, and a second (domain-expert) review of the question set.
- **A corrected error:** an nDCG calculation error found on 16 Nov was fixed and the affected results recomputed;
  older entries in `results.json` that still carry the wrong values are marked `known_issue`.

## Reproducing

The repository has the code, the questions (`eval/questions.jsonl`, `eval/splits.json`) and the results; it does not have the
source PDFs, chunks or indexes (they are the publishers' text). To rebuild, download the six documents listed in `corpus.yaml`
by hand into `docs/` (there is no download script yet; `corpus.yaml` pins a SHA-256 for each file), then:

```
uv sync
uv run python -m rag.parse                  # PDFs in docs/ to per-page markdown
uv run python -m rag.clean flag             # flag low-text pages; approved drops live in pages_to_drop.yaml
uv run python -m rag.clean run
uv run python -m rag.chunk                  # data/chunks.jsonl
uv run python -m rag.table_summary          # optional, calls the LLM (needs OPENAI_API_KEY in .env); see config.py
uv run python -m rag.index                  # Chroma and BM25 indexes under index/
uv run python eval/retrieval_eval.py --split dev --tag mine
uv run python eval/agent_run.py --split dev --tag mine
uv run pytest
```

These commands are listed from the project's own build log and have not been re-run on a fresh clone (that test is not done).
The docstring at the top of each script in `eval/` is the reference. The table summaries are LLM output stored
in `data/` (not committed), so an index rebuilt without them will not match the reported table results exactly.
Results are written to `results/results.json`; this README is regenerated with `uv run python eval/make_readme.py`.

## Stack

Python 3.11+, uv, PyMuPDF / pymupdf4llm, ChromaDB, bm25s, sentence-transformers (bge-small, MiniLM cross-encoder), LangChain
(model access, messages, tool calling), LangGraph (agent graph), OpenAI models (gpt-5-nano, gpt-5-mini), pydantic, tenacity,
pytest, ruff.
